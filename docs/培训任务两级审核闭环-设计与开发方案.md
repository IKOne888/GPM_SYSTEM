# 培训任务两级审核闭环 —— 设计与开发方案

> 版本：v1.0
> 适用范围：管理端（frontend-pc）、学员端（frontend-student）、微信小程序（miniprogram）、后端（backend）
> 关联文档：《功能设计报告.md》《微信小程序-设计与开发方案.md》

---

## 一、背景与问题

### 1.1 现状诊断

培训计划（`tr_training_plan`）已有完整审批流，但培训任务（`tr_training_task`）**没有任何审核/验收环节**，任务完成完全由学员行为自动触发。

**（1）培训计划审批 —— 已实现 ✓**

`TrTrainingPlanServiceImpl` 中已定义状态常量：

| 常量 | 值 | 含义 |
| --- | --- | --- |
| STATUS_DRAFT | 0 | 草稿 |
| STATUS_PENDING | 1 | 待审批 |
| STATUS_APPROVED | 2 | 已通过 |
| STATUS_REJECTED | 3 | 已驳回 |
| STATUS_PUBLISHED | 4 | 已发布（审批通过并完成下发后的终态） |

流转：`草稿(0) --提交审批--> 待审批(1) --审批通过--> 已发布(4)（同时自动下发任务）`，`待审批(1) --驳回--> 已驳回(3)`。
接口：`PUT /training/plans/{id}/submit`、`POST /training/plans/{id}/approve`、`POST /training/plans/{id}/reject`。

**（2）培训任务 —— 无审核环节 ✗**

`TrTrainingTask` 实体字段仅有：`name / planId / courseId / userId / taskType / source / description / status / deadline / startTime / completeTime / studyDuration / videoProgress / examScore / examPass / retryCount / maxRetry` —— **无任何审核人、审核时间、审核意见、确认状态字段**。

任务状态（`StudyServiceImpl`）：

| 常量 | 值 | 含义 | 是否落库 |
| --- | --- | --- | --- |
| STATUS_NOT_STARTED | 0 | 待学习 | 是 |
| STATUS_STUDYING | 1 | 学习中 | 是 |
| STATUS_WAITING_EXAM | 2 | 待考试 | 是 |
| STATUS_COMPLETED | 3 | 已完成 | 是 |
| STATUS_OVERDUE | 4 | 已逾期 | 否（动态计算） |

状态推进全部自动：
- 学员上报视频进度：`0 → 1`，所有视频学完（≥95%）`→ 2`
- **考试通过：`→ 3` 已完成**；考试不通过：退回 `→ 2`

管理端任务操作仅有：分配（`POST /training/tasks/assign`）、标记完成（`PUT /training/tasks/{id}/complete`）、催办（`POST /training/tasks/{id}/notify`）。其中「标记完成」会**绕过学习与考试直接置为已完成**，语义模糊（既像审核又像兜底，且无二次确认）。

### 1.2 缺陷结论

对 GMP 培训体系而言，标准闭环应为：**培训实施 → 效果评估（考试）→ 培训记录确认/审核 → 归档**。当前缺失「确认/审核」环节：

1. 实体无审核字段，无法承载审核结果与审核痕迹
2. 无「学员达标 → 待审核」中间态，学员不知道要等确认，管理员也不知道有待办
3. 管理端无待审核列表、无审核弹窗，无法体现「谁审、审什么、审没审」
4. 「标记完成」语义模糊，且一次点击即终态，不可追溯

### 1.3 附带缺陷：计划审批「自提自批」

`approve()` / `reject()` 仅校验状态为「待审批」，**不校验审批人 ≠ 提交人**。同一账号可先提交、再自己审批通过。资源权限上 `SaTokenConfig` 把计划/任务审批都给了 `SUPER_ADMIN / QA_MANAGER / TRAINING_ADMIN`，未区分「提交角色」与「审核角色」。

## 二、目标与范围

### 2.1 目标

1. 为培训任务引入**两级审核闭环**：部门主管审核 → QA（质量管理员）复核 → 归档
2. 增加明确的「待审核」中间态，学员端/小程序可见，管理端有**待办列表**
3. 审核动作全程留痕（审核人、审核时间、审核意见）
4. 审批结果通过站内信通知到相关人
5. 一并修复培训计划「自提自批」缺陷

### 2.2 不在本次范围

- 三级及以上审核、会签、代理审核
- 审核超时自动通过/升级
- 电子签名、审计追踪页面改造（仅沿用现有审计日志切面）

## 三、总体设计

### 3.1 角色与职责

| 角色编码 | 角色名称 | 在审核链中的职责 |
| --- | --- | --- |
| EMPLOYEE | 普通员工 | 学习 + 考试，触发进入审核链 |
| DEPT_LEADER | 部门负责人 | **一级审核**：审核本部门学员的培训完成情况，通过或退回 |
| QA_MANAGER | 质量管理员 | **二级复核**：复核主管已通过的记录，通过后归档；可退回 |
| TRAINING_ADMIN | 培训管理员 | 计划/任务维护、分配、催办；可代行审核（兜底） |
| SUPER_ADMIN | 系统管理员 | 全部权限，最终兜底 |

> 一级审核人定位规则：任务所属学员所在部门中 `sys_user.is_department_leader = 1` 的用户。
> 若该部门无主管，则退回给培训管理员/系统管理员兜底，并在待办中标注。

### 3.2 状态机设计

保留原 `status`（学习执行状态）不变，**新增 `review_status`（审核状态）** 作为独立维度，避免重编号影响逾期动态计算等既有逻辑。

```
                     学员学习 + 考试通过
status: 2 待考试 ─────────────────────────► status = 3（学习执行达标）
                                              review_status = 0  待主管审核
                                                    │
                                    ┌───────────────┴───────────────┐
                          主管审核通过│                               │主管退回
                                    ▼                               ▼
                        review_status = 1                  review_status = 3
                           待 QA 复核                          已退回
                                    │                    status 回退为 2（待考试）
                    ┌───────────────┴───────────────┐        允许重新考试
           QA 通过  │                               │ QA 退回
                    ▼                               ▼
        review_status = 2                      review_status = 3
          已复核通过（归档）                        已退回 → status = 2
                    │
                    ▼
            任务终态：status = 3 + review_status = 2
```

**review_status 取值定义**：

| 值 | 含义 | 说明 |
| --- | --- | --- |
| NULL | 不适用 | 尚未进入审核链（学习/考试未达标），或历史数据 |
| 0 | 待主管审核 | 学习与考试已达标，等待部门主管审核 |
| 1 | 待 QA 复核 | 主管已通过，等待质量管理员复核 |
| 2 | 已复核通过 | 两级均通过，任务归档完成 |
| 3 | 已退回 | 主管或 QA 退回，需重新学习/考试 |

**展示状态码（statusCode / status 字符串）扩展**：

| statusCode | status 字符串 | 展示文案 | 判定条件 |
| --- | --- | --- | --- |
| 0 | not_started | 待学习 | status = 0 |
| 1 | studying | 学习中 | status = 1 |
| 2 | waiting_exam | 待考试 | status = 2 |
| 3 | completed | 已完成 | status = 3 且（review_status IS NULL 或 = 2） |
| 4 | overdue | 已逾期 | 未进入审核链 且 已过截止时间 |
| 5 | pending_leader_review | 待主管审核 | status = 3 且 review_status = 0 |
| 6 | pending_qa_review | 待 QA 复核 | status = 3 且 review_status = 1 |
| 7 | rejected | 已退回 | status = 3 且 review_status = 3 |

> 兼容规则：`review_status IS NULL 且 status = 3` 视为已完成（保护历史数据），无需数据回填。
> 逾期规则：进入审核链（review_status 非 NULL）后不再判定逾期，避免「已完成却在走审核时显示逾期」的歧义。

### 3.5 通知设计

统一使用 `SysMessageService.send(...)`（现有消息类型：1-培训任务 TYPE_TASK、2-到期提醒 TYPE_EXPIRE、3-补考 TYPE_RETAKE、4-系统 TYPE_SYSTEM）。

| 触发时机 | 接收人 | 标题 / 内容要点 |
| --- | --- | --- |
| 学员达标进入审核链 | 部门主管 | 「培训记录待审核」：某某完成了《任务名》，请审核 |
| 主管审核通过 | QA_MANAGER | 「培训记录待复核」：某某的《任务名》已通过主管审核，请复核 |
| 主管 / QA 退回 | 学员 | 「培训记录被退回」：附退回意见，请重新学习考试 |
| QA 复核通过 | 学员 | 「培训已完成归档」：恭喜，培训记录已归档 |
| 部门无主管 | TRAINING_ADMIN / SUPER_ADMIN | 「待审核任务缺少部门主管」：请指定审核人或代审 |

## 四、关键交互流程

### 4.1 后台管理员分配任务（现有，保持）

1. 培训任务页 → 「分配培训任务」/「批量分配」→ 选课程、执行人、截止日期
2. `POST /training/tasks/assign` → 按执行人拆分为多条任务（`status=0`）→ 发站内信
3. 学员端可见任务并开始学习

### 4.2 学员完成任务并进入审核链

1. 学员播放视频 → 进度上报 → `status: 0→1→2`
2. 学员考试通过 → `status=3`，**同时置 `review_status=0`**，向部门主管发待审核站内信
3. 学员端任务状态显示「待主管审核」，只读提示「培训已完成，等待审核中」

### 4.3 主管审核

1. 主管登录管理端 → 「培训任务」页（或待办徽标）→ 筛选 `reviewStatus=0`（仅本部门）
2. 点「审核」→ 弹窗展示学习时长、视频进度、考试成绩、是否通过
3. 通过 → `review_status=1`，通知 QA；退回（必填意见）→ `review_status=3`、`status=2`，通知学员

### 4.4 QA 复核

1. QA 登录 → 「培训任务」页 → 筛选 `reviewStatus=1`
2. 通过 → `review_status=2`（归档），通知学员；退回（必填意见）→ `review_status=3`、`status=2`，通知学员

### 4.5 退回后重新考试

学员端任务回到「待考试」，可重新进入考试；`/study/exams/{taskId}/start` 的拦截条件放宽为「已通过 **且** 未被退回」时禁止。重新考试通过后 `review_status` 重置为 `0`，重新走审核链。

## 五、权限设计

### 5.1 Sa-Token 规则调整（`SaTokenConfig`）

现有：

```
/training/tasks, /training/tasks/** → SUPER_ADMIN / QA_MANAGER / TRAINING_ADMIN
```

调整方案（新增独立审核路径，避免放开整个培训任务模块给 DEPT_LEADER）：

```
# 审核相关接口：主管与 QA 均可访问，具体阶段校验在 Service 层按角色严格区分
/training/tasks/review/**, /training/tasks/*/leader-review, /training/tasks/*/qa-review
    → SUPER_ADMIN / QA_MANAGER / TRAINING_ADMIN / DEPT_LEADER
```

> Service 层二次校验：`leader-review` 调用者必须是 `DEPT_LEADER`（或管理员兜底）且与学员同部门；`qa-review` 调用者必须是 `QA_MANAGER`（或 SUPER_ADMIN 兜底）。**权限不能只靠路由，必须在 Service 层做身份校验。**

### 5.2 管理端路由（`frontend-pc/src/router/index.js`）

- 保持「培训管理」菜单 `ROLE_GROUPS.TRAINING` 不变（管理员级）
- 新增 `ROLE_GROUPS.REVIEW = ['SUPER_ADMIN','QA_MANAGER','TRAINING_ADMIN','DEPT_LEADER']`
- 「培训任务」页面内的审核按钮按 `roles + reviewStatus` 双重控制显隐：
  - 「主管审核」按钮：`reviewStatus === 0` 且角色含 `DEPT_LEADER/TRAINING_ADMIN/SUPER_ADMIN`
  - 「QA 复核」按钮：`reviewStatus === 1` 且角色含 `QA_MANAGER/TRAINING_ADMIN/SUPER_ADMIN`

> 若需 DEPT_LEADER 能进入「培训任务」菜单，则需把 `DEPT_LEADER` 加入该路由的 roles——渲染前需确认菜单可见性与数据隔离（后端仅返回本部门数据）同步生效。

## 九、验收标准

1. 学员考试通过后，任务进入「待主管审核」，部门主管收到站内信
2. 非本部门主管无法审核该任务（接口返回明确拒绝信息）
3. 主管通过后进入「待 QA 复核」，QA 收到站内信
4. QA 通过后任务为「已完成（已归档）」，学员收到通知
5. 主管或 QA 退回时必填意见，任务回到「待考试」，学员可重新考试，重考通过后重新进入「待主管审核」
6. 同一账号不能审批自己提交的培训计划（返回明确错误）
7. 学员端与小程序正确显示 7 种状态文案；历史已完成任务不受影响
8. 后端编译打包、两前端构建、小程序路径一致性检查全部通过

## 十、已确认决策

1. **「部门主管」定位**：优先取学员所在部门中 `sys_user.is_department_leader = 1` 的用户作为一级审核人；
   若该部门不存在主管，则回退给 `TRAINING_ADMIN / SUPER_ADMIN` 兜底，并在待办列表中标注「缺少部门主管」。
2. **主管审核入口**：在「培训任务」页内新增「待我审核」选项卡（不放开「培训管理」菜单给 DEPT_LEADER，也不新增独立菜单）；
   后端对 DEPT_LEADER 强制部门数据隔离（仅返回本部门任务）。
3. **「标记完成（免考确认）」权限**：仅限 `TRAINING_ADMIN / SUPER_ADMIN`，且**必须填写确认理由**（写入 `qa_review_remark`），
   执行后直接置 `status=3, review_status=2`（视为已归档）。
