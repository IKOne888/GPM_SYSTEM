# GMP 培训系统 · 用户端与管理端功能补全 设计与开发方案

> 版本：v1.0
> 编写日期：2026-10-13
> 关联文档：《功能设计报告.md》《培训任务两级审核闭环-设计与开发方案.md》《管理端-新功能-设计与开发方案.md》
> 适用范围：`backend`（8080）、`frontend-pc`（管理端 3000）、`frontend-student`（学员端 3002）、`miniprogram`（微信小程序）

---

## 1. 背景与目标

### 1.1 背景

培训任务两级审核闭环已交付并实测通过。经对两端功能点做逐项核查，发现以下四处**链路断裂或功能缺失**：

| 编号 | 现象 | 影响 |
| --- | --- | --- |
| 问题 1 | 管理端已有「培训需求」页（登记 / 采纳 / 拒绝），但**学员端无任何提交入口** | 需求只能由管理员代录，学员无法自下而上提出培训诉求，需求台账失真 |
| 问题 2 | 管理端侧栏用户下拉的「个人中心」是 `TODO` 注释，**无跳转目标与页面** | 管理员无法自助维护手机号/邮箱，也无法自助改密，必须超管代改 |
| 问题 3 | 站内信（`sys_message`）仅由系统事件自动触发（任务分配、审核、催办），**管理员无手工发布入口** | 无法下发制度通知、临时培训安排等运营公告 |
| 问题 4 | 待审核任务、待处理需求、待审批计划**分散在三个菜单**，无统一入口 | 管理员每天需逐个菜单巡检，容易漏办 |

### 1.2 目标

1. 打通「学员提需求 → 管理员处理 → 通知学员」的完整闭环；
2. 补齐管理端个人中心，消除 `TODO`；
3. 提供管理员公告发布能力（全员 / 按部门 / 按岗位定向）；
4. 提供统一待办中心，聚合三类待办并支持一键跳转。

### 1.3 边界（本次不做）

- 不做公告的富文本编辑器与图片上传（纯文本标题 + 正文）；
- 不做待办中心的消息推送与邮件提醒；
- 不做需求附件的上传；
- 不改动任何既有接口的路径与返回结构（只新增）。

## 2. 功能一：学员端「培训需求申报」

### 2.1 现状分析

- 表：`tr_training_demand`（`title` / `content` / `training_topic` / `training_target` / `reason` / `department_id` / `status` / `create_by` / `deleted`）；
- 状态：`0-待处理` `1-已采纳` `2-已拒绝`，处理意见复用 `reason` 字段；
- 后端仅 `/training/demands`（管理员角色），学员端 `/study/**` 下**无需求相关接口**；
- `create_by` 由 MyBatis-Plus 自动填充为**登录账号 username**，无用户ID，无法据此可靠地向提交人回发站内信。

### 2.2 数据库变更

对 `tr_training_demand` 增加提交人字段：

| 字段 | 类型 | 允许空 | 说明 |
| --- | --- | --- | --- |
| `submit_user_id` | bigint | 是 | 提交人用户ID；学员端提交时写入，用于「我的申报」数据隔离与处理结果通知 |

> 索引：`idx_demand_submit_user (submit_user_id)`。
> 存量数据：`submit_user_id` 保持 `NULL`（均为管理端代录），管理端列表展示不受影响；仅「我的申报」按 `submit_user_id` 过滤，故不会显示存量代录数据。

### 2.3 接口契约（新增，位于 `/study/**`）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/study/demands` | 分页查询**本人提交**的需求（强制 `submit_user_id = 当前登录用户`） |
| GET | `/study/demands/{id}` | 查询本人需求详情（非本人返回 403） |
| POST | `/study/demands` | 提交培训需求（状态固定为 `0-待处理`） |

**POST `/study/demands` 请求体**

```json
{
  "title": "无菌区更衣流程专项培训",
  "content": "近期新员工对更衣流程不熟悉，建议开展专项培训并考核。",
  "trainingTopic": "无菌操作规范",
  "trainingTarget": "生产部新入职员工"
}
```

**服务端强制规则**

- `status` 固定写入 `0`，**忽略客户端传值**，防止学员自封「已采纳」；
- `departmentId` 取当前登录用户的 `sys_user.department_id`，不信任客户端；
- `submit_user_id` 取 `StpUtil.getLoginIdAsLong()`；
- `title` 必填且 ≤100 字符，`content` 必填且 ≤1000 字符。

### 2.4 处理结果通知（闭环关键）

在管理端 `TrTrainingDemandServiceImpl.handleDemand(id, dto)` 处理完成后：

- 若 `submit_user_id != null`，调用
  `SysMessageService.send(submitUserId, TYPE_SYSTEM, "培训需求处理结果", "您提交的需求《{title}》已{采纳/拒绝}：{reason}", demandId)`；
- `submit_user_id == null`（管理端代录）时跳过通知，保持原行为不变。

### 2.5 前端页面

**PC 学员端（frontend-student）**

- 新增 `src/views/demand/index.vue`：分为「统计条（待处理 / 已采纳 / 已拒绝）」+「我的申报列表」+「提交需求弹窗」；
- 新增 `src/api/demand.js`：`getMyDemands` / `getDemandDetail` / `submitDemand`；
- 路由新增 `/demands`，侧栏菜单「需求申报」（icon 建议 `ChatLineSquare`）；
- 交互：提交成功后刷新列表并提示「已提交，等待培训管理员处理」。

**微信小程序（miniprogram）**

- 新增 `pages/demand/list`（我的申报列表 + 状态标签）与 `pages/demand/submit`（提交表单）；
- 在 `pages/profile/index` 增加「需求申报」入口；
- `app.json` 的 `pages` 数组追加两个页面路径。

### 2.6 数据隔离

由 **Service 层** 通过 `StpUtil.getLoginIdAsLong()` 强制过滤，不依赖前端传参：

- 列表：`.eq(TrTrainingDemand::getSubmitUserId, currentUserId)`；
- 详情：查询后校验 `submitUserId` 与当前用户一致，否则抛 `ErrorCode.FORBIDDEN`。

## 3. 功能二：管理端「个人中心」

### 3.1 现状分析

- `frontend-pc/src/layout/index.vue` 的 `handleCommand` 中 `case 'profile': // TODO: 跳转个人中心`，无页面；
- `AuthController` 仅有 `/auth/captcha`、`/auth/login`、`/auth/logout`，**无个人资料与改密接口**；
- `SysUserController` 的 `/{id}/reset-password` 是**超管重置他人密码**，不能用于自助改密。

### 3.2 接口契约（新增，位于 `/auth/**`，登录即可访问）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/auth/profile` | 查询当前登录用户资料 |
| PUT | `/auth/profile` | 修改个人资料（`realName` / `phone` / `email`） |
| PUT | `/auth/password` | 修改本人密码 |

**GET `/auth/profile` 返回**

```json
{
  "id": 1, "username": "admin", "realName": "超级管理员",
  "phone": "13800000000", "email": "admin@gmp.com",
  "departmentId": 2, "departmentName": "质量部",
  "positionId": 1, "positionName": "质量经理",
  "roles": ["SUPER_ADMIN"], "lastLoginTime": "2026-10-13 13:00:01", "status": 1
}
```

**PUT `/auth/password` 请求体**

```json
{ "oldPassword": "admin123", "newPassword": "gmp2026ok", "confirmPassword": "gmp2026ok" }
```

**服务端校验**

- 旧密码必须与库中 BCrypt 密文匹配，否则 `3003 原密码错误`；
- 新密码需满足既有强度约定：**6-20 位且同时包含字母与数字**，否则 `400`；
- `newPassword` 与 `confirmPassword` 必须一致，否则 `400`；
- 新密码不得与旧密码相同，否则 `3003 新密码不能与原密码相同`；
- 改密成功后**不强制下线**（保持 Sa-Token 会话），仅返回成功。

### 3.3 安全说明（重要）

`SaTokenConfig` 的白名单仅放行 `/auth/login` 与 `/auth/captcha`，`/auth/**` 其余路径均由全局 `checkLogin` 兜底，因此新增的 `/auth/profile`、`/auth/password` **必须登录后才可访问**，不存在越权风险。**严禁**将这两个路径加入白名单。

### 3.4 前端页面

- 新增 `frontend-pc/src/views/profile/index.vue`：左右两块卡片
  - 「基本资料」：用户名（只读）、姓名、手机号、邮箱、部门 / 岗位（只读）、角色（只读标签）；
  - 「修改密码」：原密码、新密码、确认新密码；
  - 顶部展示头像、用户名、角色标签与上次登录时间。
- `layout/index.vue` 的 `case 'profile'` 改为 `router.push('/profile')`；
- 路由新增 `/profile`（`meta.title = '个人中心'`，`meta.hidden = true`，不加 `roles` 限制 → 登录即可访问）。

## 4. 功能三：管理端「通知公告发布」

### 4.1 现状分析

- `sys_message` 表承载站内信，`SysMessageService.send(userId, messageType, title, content, relatedId)` 为唯一写入入口；
- 现有消息类型：`1-任务通知` `2-到期提醒` `3-补考提醒` `4-系统通知`；
- 管理端**无任何手工发布入口**。

### 4.2 数据库变更

**无新增表**，完全复用 `sys_message`。公告以 `message_type = 4`（系统通知）入库，`related_id` 置空。

### 4.3 接口契约（新增，`/system/notices`）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/system/notices` | 发布公告 |
| GET | `/system/notices` | 查询公告发布历史（可选，按发布时间倒序分页） |
| GET | `/system/notices/targets` | 查询可选目标（部门列表 / 岗位列表），供前端下拉 |

**POST `/system/notices` 请求体**

```json
{
  "title": "关于 2026 年度 GMP 复训安排的通知",
  "content": "请各部门于 10 月 31 日前完成复训报名……",
  "targetType": 2,
  "targetIds": [2, 4]
}
```

`targetType` 语义：`1-全员`、`2-按部门`、`3-按岗位`。

**服务端规则**

- 解析目标用户ID集合：
  - `1-全员` → 所有 `status = 1` 的用户；
  - `2-按部门` → `department_id IN (targetIds)` 的用户；
  - `3-按岗位` → `position_id IN (targetIds)` 的用户；
- `targetType != 1` 时 `targetIds` 不得为空，否则 `400 请选择接收对象`；
- 目标用户为空时抛 `3003 未匹配到任何接收人，请检查接收范围`；
- 逐条调用 `SysMessageService.send(userId, TYPE_SYSTEM, title, content, null)`；
- `title` 必填 ≤100，`content` 必填 ≤1000；
- 返回 `Result.success()` 并在 `message` 中回显实际触达人数（如「已发送给 12 人」）。

### 4.4 权限

`SaTokenConfig` 现有规则 `SaRouter.match("/system/**", ...)` 放行了 `SUPER_ADMIN / QA_MANAGER / TRAINING_ADMIN / DEPT_LEADER`。公告发布**不应开放给部门负责人**，故需新增更严格的规则：

```
SaRouter.match("/system/notices", "/system/notices/**")
        .check(r -> StpUtil.checkRoleOr("SUPER_ADMIN", "QA_MANAGER", "TRAINING_ADMIN"));
```

> 该规则必须在 `/system/**` 通用规则之后、且因 Sa-Token 同为「满足任一角色」累加校验，部门负责人会在第二条规则上被拒绝——与既有 `/system/department` 写操作的处理方式保持一致。

### 4.5 前端页面

- 新增 `frontend-pc/src/views/system/notice/index.vue`：左侧发布表单（标题、正文、接收范围单选 + 部门/岗位多选），右侧发布历史列表；
- 路由新增 `/system/notice`，`meta.title = '通知公告'`，`meta.roles = ROLE_GROUPS.TRAINING`（管理员三角色，与后端一致）。

## 5. 功能四：管理端「统一待办中心」

### 5.1 现状分析

三类待办分散：

| 待办类型 | 数据来源 | 现状入口 |
| --- | --- | --- |
| 待审核任务 | `tr_training_task.review_status IN (0,1)` | 培训任务页「待我审核」页签 |
| 待处理需求 | `tr_training_demand.status = 0` | 培训需求页 |
| 待审批计划 | `tr_training_plan.status = 1` | 培训计划页 |

### 5.2 接口契约（新增，`/dashboard/todo`）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/dashboard/todo` | 聚合待办统计 + 各类型 Top5 明细 |

**返回结构**

```json
{
  "reviewPending": { "count": 3, "items": [ { "id": 9, "title": "无菌区GMP基础培训", "extra": "设备部 · 学员 商乐", "time": "2026-10-13 13:00:01", "stage": "leader" } ] },
  "demandPending": { "count": 2, "items": [ { "id": 12, "title": "更衣流程专项培训", "extra": "提交人 商乐", "time": "2026-10-13 12:00:00" } ] },
  "planPending":   { "count": 1, "items": [ { "id": 7, "title": "2026年度设备部培训计划", "extra": "提交人 admin", "time": "2026-10-13 10:00:00" } ] },
  "total": 6
}
```

**统计口径（按当前登录用户角色自适应）**

| 角色 | 待审核任务范围 | 待处理需求 | 待审批计划 |
| --- | --- | --- | --- |
| `DEPT_LEADER` | 仅本部门 `review_status = 0` | — | — |
| `QA_MANAGER` | 全局 `review_status = 1`（复核） | 全部 `status = 0` | 全部 `status = 1` |
| `TRAINING_ADMIN` | 全局 `review_status IN (0,1)` | 全部 `status = 0` | 全部 `status = 1` |
| `SUPER_ADMIN` | 全局 `review_status IN (0,1)` | 全部 `status = 0` | 全部 `status = 1` |

> 待审核任务复用已交付的 `TrTrainingTaskService.reviewStats()` 与 `pendingReviews()`，避免重复实现口径。

### 5.3 权限

`/dashboard/todo` 仅需登录（`SUPER_ADMIN / QA_MANAGER / TRAINING_ADMIN / DEPT_LEADER` 均可），**不新增角色规则**，由全局 `checkLogin` 兜底；内容按角色范围过滤在 Service 层完成。

### 5.4 前端页面

- 新增 `frontend-pc/src/views/todo/index.vue`：三张待办卡片分区展示，每区顶部为计数徽标 + 「查看全部」按钮（跳对应菜单并带筛选参数），下方为 Top5 列表；
- 路由新增 `/todo`，`meta.title = '待办中心'`，`meta.icon = 'Bell'`，放在「首页」之后作为一级菜单；
- 点击明细项：审核 → 跳 `/training/task?tab=review`；需求 → `/training/demand?status=0`；计划 → `/training/plan?approvalStatus=1`。

## 9. 开发顺序

1. 增量 SQL 脚本（`tr_training_demand.submit_user_id` + 索引）并执行；
2. 后端：学员端需求申报接口 + 管理端处理结果通知；
3. 后端：个人中心三个接口；
4. 后端：通知公告发布接口；
5. 后端：统一待办中心接口 + `SaTokenConfig` 权限规则；
6. 前端 PC：个人中心（含 `layout` 的 TODO 修复）→ 通知公告 → 待办中心；
7. 前端学员端：需求申报页（含 API 与路由菜单）；
8. 小程序端：需求申报列表与提交页，`pages/profile/index` 加入口；
9. 编译构建（后端 / PC / 学员端）+ 接口实测（对照第 8 章用例）。

## 10. 风险与注意事项

1. **`/auth/**` 白名单不可扩大**：个人中心接口一旦误入白名单将导致未登录可改密；
2. **`/system/notices` 规则顺序**：必须写在 `/system/**` 通用规则之后，否则通用规则先放行会失去收紧效果；
3. **需求表存量数据**：`submit_user_id` 保持 `NULL`，不回填，避免把管理端代录记录错误归属到某个学员；
4. **待办口径复用**：待审核任务统计必须复用 `TrTrainingTaskService` 既有方法，避免与培训任务页数字不一致；
5. **公告批量发送性能**：目标用户较多时逐条 `insert`，单次公告建议目标不超过 500 人；后续如需优化可改为批量插入；
6. **个人中心改密后会话**：本次不改会话，若后续要求「改密后强制重新登录」需另行调整。
